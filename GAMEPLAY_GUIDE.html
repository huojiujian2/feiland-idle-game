优点（保持不变）

  • 词条系统深度足够：200 词条 × 主动/被动 × 4 级，搭配空间大

核心问题诊断

问题严重程度说明
挂机过于被动，玩家无决策点高自动战斗无策略选择，长时间无操作 = 无聊
战斗缺乏可视化反馈高文字日志单调，无伤害数字、无特效、无音效
无社交/竞争内容高单机游戏，无排行榜、无公会、无 PVP，留存动力弱
装备获取途径单一中只有打怪掉落，无锻造/合成/抽卡，装备获取不可控
后期内容断层中Lv.90→100 区域只有 2 个，登神后无新内容
材料用途单一中材料只用于附魔和种族进化，无锻造/合成/任务
无新手引导/教程中新玩家不知道该做什么，职业/词条选择无参考
词条效果不透明中词条加成在战斗中不可见，玩家无法感知词条价值
无成就/里程碑系统低缺乏长期目标和奖励反馈
无每日活动/限时事件低日复一日挂机无变化，缺乏新鲜感
核心结论：游戏框架完整、数据量充足，但缺少让玩家「主动参与」的机制。 当前是一个「挂着不动」的被动游戏，需要向「挂着但有选择」的主动游戏转型。 以下按优先级从高到低排列改进方向。

2战斗系统深化

2.1 战斗可视化与反馈

T-001 战斗伤害数字飘字 高优先
在战斗日志上方/侧边添加浮动伤害数字（红色物理伤害、蓝色魔法伤害、绿色治疗、黄色暴击放大字号）。 数字应从出现位置向上飘移并淡出，持续约 1.5 秒。 暴击时字号更大 + 抖动效果。

技术要点

  • 在 MapView.vue 的战斗区域添加一个 overlay canvas 或 div 层
  • engine.js 的 calculateIdle() 返回的 battle logs 已包含伤害数据，前端消费即可
  • 用 CSS animation 实现 translateY(-60px) + opacity 0→1→0
  • 暴击伤害用 transform: scale(1.3) + 红色加粗
涉及文件： client/src/components/MapView.vue client/src/style.css
T-002 战斗动作动画与特效 高优先
角色和怪物在攻击时有简单的视觉反馈：攻击方向前冲、防御方被打退/闪白。 可用 CSS transform（translateX + 回弹）实现。 技能释放时添加全屏滤镜（雷霆=闪白、火焰=橙红叠加、冰=蓝白叠加）。

建议方案

  • 角色头像/怪物名加 class="attack-anim" → CSS keyframe 抖动
  • 技能特效用 position: absolute 全屏 div，0.3s 淡入淡出
  • 在 MapView 的 battle log 渲染时，根据 log.type 和 log.skill 触发对应动画
T-003 战斗BGM与音效 低优先
添加背景音乐（可使用免费授权素材）和关键音效：攻击、暴击、升级、装备掉落、死亡。 用 HTML5 Audio API，在对应事件触发时播放。 提供静音开关。

2.2 战斗策略与决策

T-004 战斗策略模式选择 高优先
让玩家在挂机前选择战斗策略，赋予主动决策权。策略影响自动战斗的行为：
策略效果解锁条件
全力进攻ATK+15%，DEF-10%，适合碾压初始
稳健防守DEF+15%，ATK-10%，回复+50%初始
平衡无加成无减成（默认）初始
贪婪掠夺GOLD+30%，EXP-20%，掉落率+5%Lv.20
背水一战ATK+40%，DEF-30%，HP<30%时再加20%Lv.40
极限修炼EXP+50%，GOLD-50%，怪物ATK+20%Lv.60

技术要点

  • 在 server/engine.js 的 calculateIdle() 中读取 player.strategy 并应用修正
  • 在 server/index.js 添加 POST /api/player/:username/strategy 接口
  • 在 MapView.vue 区域选择上方添加策略切换按钮组
  • 策略切换免费但 5 分钟 CD（防频繁切换）
T-005 手动技能释放（主动词条实战） 高优先
当前主动词条仅做被动加成，未在战斗中体现主动技能效果。应改为： 每 N 回合自动释放主动词条技能（或手动点击释放），产生实际战斗效果（伤害倍率、治疗、增益 buff）。
词条效果已在 data.js 的 AFFIX_TREE 中定义了 effect.type（damage/heal/buff 等）， 需要在 engine.js 的战斗计算中实现这些 effect 的实际逻辑。

实现步骤

  1. 在 calculateIdle() 的每回合循环中，检查玩家装备的主动词条
  2. 根据词条 effect.type 执行对应逻辑：
    • damage：在普通攻击后追加 ATK × mult 的技能伤害
    • heal：恢复 maxHP × value
    • atk_buff / def_buff / agi_buff：临时提升对应属性，持续 turns 回合
    • gold_buff：本场战斗 GOLD 获取 ×(1+value)
  3. 技能 CD：初级 5 回合、中级 4 回合、高级 3 回合、大师 2 回合
  4. 在战斗日志中添加 type: 'skill' 类型的日志，前端特殊渲染
T-006 BOSS 战与精英怪 中优先
每个区域添加 1 个 BOSS 和 2 个精英怪。BOSS 定时刷新（每 2 小时一次）， 掉落更丰厚（必掉稀有装备/材料）。精英怪概率出现（10%），属性 ×2，掉落 ×3。

数据结构建议

T-007 战斗结算评级（DPS / 用时 / 评价） 低优先
每场战斗结束后显示评级：S/A/B/C/D，基于剩余 HP 比例 + 用时 + 是否被技能命中。 评级影响额外掉落率（S 级 +10% 掉落）。

3成长与进阶体系

T-010 转生/轮回系统 高优先
Lv.100+ 玩家可「转生」：等级重置为 1，但保留部分加成（转生点数）， 每次转生获得 1 点转生点，可投入永久属性树。转生次数越多，后续成长越快。
这是放置游戏的核心留存机制 —— 给老玩家「重新开始但更强」的体验。

永久属性树（转生点商店）

节点消耗效果
先天之力1点ATK 基础+5%（可升5级）
先天之体1点HP 基础+5%（可升5级）
先天之速1点AGI 基础+5%（可升5级）
经验加速2点EXP 获取+10%（可升3级）
金币天赋2点GOLD 获取+10%（可升3级）
词条扩展3点被动词条槽+1（可升2级）
初始等级2点转生后从 Lv.10 开始（可升3级→Lv.30）
暴击觉醒3点暴击率+3%（可升3级）

技术要点

  • 在 player 对象添加 reincarnation: 0, reincPts: 0, reincTree: {}
  • engine.js 添加 reincarnate(player) 函数：重置等级/经验/属性，保留装备/词条/金币
  • 在 EvolutionView.vue 添加转生入口（Lv.100+ 显示）
  • 转生后全属性 = 基础 × (1 + 转生加成 + 职业系数) + 装备 + 词条 + 附魔 + 法则 + 神性
T-011 属性突破与上限提升 中优先
登神后引入「属性突破」机制：消耗信仰点和法则碎片，可突破单项属性上限。 每个属性可突破 10 次，每次消耗递增。
突破 1：消耗 100 信仰 + 3 法则碎片 → ATK 上限 +10%
突破 2：消耗 200 信仰 + 5 法则碎片 → ATK 上限 +20%
...以此类推
T-012 新区域：深渊核心 & 神域 中优先
登神后无新内容是严重断层。添加 2 个终局区域：
区域等级要求怪物特色
深渊核心Lv.120（半神）深渊领主·完全体、虚空支配者、混沌魔神掉落「神性碎片」用于属性突破
神域战场Lv.150（神灵）堕落神灵、神罚执行者、太古巨神掉落「创世碎片」用于解锁新神格

新神格系统

  • 雷神格：雷霆系登神后解锁，ATK+30%，暴击伤害+50%
  • 光神格：光明系登神后解锁，DEF+30%，每回合回血5%
  • 风神格：风行系登神后解锁，AGI+30%，闪避+15%
  • 战神格：骑士系登神后解锁，HP+50%，免死+1次/场
  • 炼神格：炼金系登神后解锁，GOLD+50%，EXP+30%
T-013 装备锻造与合成系统 中优先
当前装备只能打怪掉落和商店买。添加锻造系统：
  • 材料锻造：消耗 3 个同级装备 + 材料 → 1 个高一级装备（例如 3 个 fine → 1 个 epic）
  • 装备升级：消耗材料 + 金币 → 装备 stats +10%（可升 5 级，每级消耗递增）
  • 装备分解：不需要的装备 → 分解为材料（对应品质的碎片）
  • 套装系统：同系列装备 2 件/3 件触发套装效果（例如「雷霆套装」2件 ATK+10%，3件暴击+5%）

技术要点

  • 在 server/data.js 添加 FORGE_RECIPES 和 EQUIP_UPGRADE 配置
  • 在 server/engine.js 添加 forgeEquips(), upgradeEquip(), disassembleEquip() 函数
  • 在 InventoryView.vue 添加「锻造」子标签页
  • 装备对象添加 upgradeLevel: 0 和 setId: null 字段

4经济系统与交易

T-020 拍卖行/交易市场 高优先
玩家可以将装备/材料挂到拍卖行出售，其他玩家可以购买。 这是 MMO RPG 的核心社交经济系统，能极大提升玩家间的互动。

功能设计

  • 上架：选择装备/材料 → 设定价格 → 上架（收取 5% 手续费）
  • 搜索：按品质/类型/等级筛选，按价格排序
  • 购买：直接支付金币购买，物品转入背包
  • 下架：可随时取消上架
  • 上架上限：同时最多 10 件
  • 价格范围：系统建议价格 ×(0.5~2.0)，防止恶意定价

技术要点

  • 在 server/store.js 添加 marketplace: [] 存储上架物品
  • 在 server/index.js 添加 GET/POST /api/market 接口
  • 新建 client/src/components/MarketView.vue 组件
  • 在 App.vue 的 TabBar 添加「市场」入口
  • 当前 JSON 存储即可支撑，后期迁 MySQL 后添加索引
T-021 每日签到与活跃度奖励 中优先
每日签到送金币/材料/经验卷轴，连续签到奖励递增（7 天循环）。 每日活跃度：完成 3 场战斗/分配 1 次属性/装备 1 个词条 = 活跃度， 累积到 30/60/100 分别领取宝箱。
T-022 抽卡/祈愿系统 中优先
消耗金币（或钻石）进行祈愿，随机获得装备/材料/词条。
祈愿类型消耗池子保底
普通祈愿5000 金币普通~精良装备/初级材料10 次必出精良
高级祈愿20000 金币精良~传说装备/中级材料20 次必出史诗
大师祈愿50000 金币史诗~传说装备/高级材料50 次必出传说
T-023 金币 sink（消耗出口） 中优先
当前金币只有买低级药剂/装备的消耗，后期金币会大量囤积无用途。添加金币消耗口：
  • 装备升级：每次 1000~10000 金币
  • 词条洗练：随机替换一个被动词条，消耗 5000 金币
  • 附魔重铸：清除一条附魔重新随机，消耗 3000 金币
  • 区域传送费：跳到非相邻区域消耗 500 金币
  • 祈愿系统（见 T-022）
  • 拍卖行手续费（见 T-020）

5社交与竞争系统

T-030 全服排行榜 高优先
排行榜是最基础也是最高性价比的社交竞争机制。实现多个维度的排行：
排行排序依据更新频率
等级排行player.level实时
战力排行总属性之和实时
金币排行player.gold实时
击杀排行累计击杀怪物数实时
转生排行reincarnation 次数实时
BOSS 击杀排行BOSS 击杀次数每周重置

技术要点

  • 在 server/index.js 添加 GET /api/leaderboard?type=level 接口
  • 遍历 store 中所有玩家，按指定字段排序，取前 100 名
  • 新建 client/src/components/LeaderboardView.vue
  • 在 App.vue TabBar 添加「排行」入口（或放在角色页内）
  • 显示排名、角色名、职业、等级、关键数值
  • 前三名特殊样式（金银铜）
T-031 PVP 竞技场 高优先
玩家可以挑战其他玩家的角色（AI 控制防守方）。挑战成功获得积分和奖励， 失败扣积分。段位制：青铜→白银→黄金→铂金→钻石→大师→宗师。

功能设计

  • 匹配：按段位±1 匹配对手（从排行数据中选取）
  • 战斗：挑战方主动操作，防守方 AI 自动（沿用现有战斗逻辑）
  • 奖励：每日前 3 场胜利有额外金币+经验奖励
  • 赛季：每月重置段位，按最终段位发放奖励
  • 防守阵容：玩家可设置防守用的词条/策略

技术要点

  • engine.js 添加 pvpBattle(attacker, defender) 函数（复用现有战斗逻辑但双方都是玩家属性）
  • player 添加 pvpScore: 1000, pvpTier: 'bronze'
  • 新建 client/src/components/ArenaView.vue
  • 添加 POST /api/pvp/challenge 接口
T-032 公会系统 中优先
玩家可创建/加入公会。公会功能：
  • 公会 BOSS：全公会成员每日可攻击 1 次，按总伤害排名发奖励
  • 公会商店：用公会贡献值兑换专属物品（公会 BOSS 掉落材料锻造的装备）
  • 公会科技：全员捐金币升级科技树（ATK/DEF/EXP/GOLD 全员加成）
  • 公会战：每周一次公会 vs 公会的战斗
公会系统复杂度较高，建议先实现排行榜（T-030）和 PVP（T-031），确认多人系统基础稳定后再做公会。
T-033 世界 BOSS / 全服事件 中优先
每天定时刷新一个全服世界 BOSS，所有玩家都可以参与攻击（每人每日 1 次）。 BOSS 被击败后，按伤害贡献分配奖励。BOSS 未被击败则全服获得减益 buff。
  • 世界 BOSS 血量 = 全服活跃玩家总战力 × 10
  • 每天 12:00 / 18:00 / 22:00 刷新 3 个不同 BOSS
  • 奖励按伤害占比分配：TOP1 得 30%，TOP10 得 20%，参与奖 10%
  • 全服事件：双倍经验时段、材料掉落加成时段（每 4 小时轮换）

8技术架构与性能

T-060 数据存储迁移到 SQLite/MySQL 中优先
当前使用 JSON 文件存储 (server/db.json)， 单文件存储在玩家数量多时会有性能和并发问题。 建议迁移到 SQLite（轻量，无需额外服务）或 MySQL（生产级）。

迁移步骤

  1. 在 server/store.js 中替换 JSON 读写为数据库操作
  2. 保持接口不变：load(), save(), getPlayer() 等
  3. 添加索引：username, level, pvpScore 等（用于排行榜查询）
  4. JSON 文件做一次数据导入到数据库
  5. 建议先用 SQLite（better-sqlite3），后续再迁 MySQL
T-061 API 限流与安全加固 中优先
当前 API 无身份验证（用 username 直接查数据），存在安全隐患。
  • 登录后返回 JWT token，后续请求需携带 token 验证身份
  • 添加 express-rate-limit 限制单 IP 每分钟请求次数
  • 关键操作（购买/出售/附魔/进化）加二次确认
  • 密码存储用 bcrypt 哈希，不明文存储
  • 输入参数校验（防注入）
T-062 实时推送（WebSocket） 低优先
当前前端定时轮询 API 获取数据（每 3 秒）。 迁移到 WebSocket 后端推送，减少无效请求，实现实时战斗日志更新。
世界 BOSS 血量、排行榜变化、拍卖行新商品等也可以实时推送。
T-063 Docker 容器化部署 低优先
添加 Dockerfile + docker-compose.yml，一键部署。 
# docker-compose.yml 示例
services:
  game-server:
    build: .
    ports:
      - "3001:3001"
    volumes:
      - ./data:/app/data
    environment:
      - NODE_ENV=production

10开发约定与注意事项

项目结构约定

  • 静态数据全部放在 server/data.js，按 CONST_NAME 大写命名
  • 游戏逻辑全部放在 server/engine.js，函数名用 camelCase
  • API 路由放在 server/index.js，RESTful 风格
  • 数据持久化在 server/store.js，保持接口不变
  • 前端组件一个功能一个 .vue 文件，放在 client/src/components/
  • 全局样式和 CSS 变量在 client/src/style.css

UI 交互规范（已确定，必须遵守）

场景形式原因
背包、技能、图鉴、地图、排行全屏替换（左右滑入滑出）沉浸式浏览
装备详情、词条详情、确认框居中弹窗（Modal）临时操作
商店购买、抽卡结果底部弹出（Action Sheet）即时反馈
  • 网格布局：4 列，每页 12 项，底部翻页器
  • 点击格子 → 弹出详情弹窗（不跳转页面）
  • 弹窗外遮罩层点击关闭
  • 动画使用 CSS 变量：var(--duration-fast/normal/slow) + var(--ease-out)
  • 颜色用主题变量：var(--accent) / var(--accent2) / var(--muted) 等，不硬编码

开发命令

pnpm install          # 安装依赖
pnpm dev              # 同时启动前后端（开发模式）
pnpm dev:server       # 单独启动后端（端口 3001）
pnpm dev:client       # 单独启动前端（端口 3000，HMR 热更新）
pnpm build            # 构建前端到 client/dist/
重要提醒
  • 不要修改 package.json 的 packageManager 字段（corepack 可能导致 pnpm 版本不匹配）
  • 不要删除 server/db.json（包含玩家存档数据）
  • 新增 API 接口后，记得在 client/src/api.js 中添加对应的前端请求方法
  • 新增组件后，在 App.vue 的 tabOrder 数组中添加对应 tab（影响滑动方向）
  • 提交代码前运行 pnpm build 确保编译通过
